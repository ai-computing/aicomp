## Question

Do the four checkpoints serve valid HTTP requests under concurrent load, cancel/disconnect and reuse? Does prefix-cache history change token output?

## Setup

Actual serve_batched.build, BatchedOwner and BatchedService with loopback HTTP sockets. GPU paged cache,4 slots,9216 context,64-token pages,256-token prefill chunks. Inputs128/2048/8192 from the same repeated-context fixture as PR203;32 output tokens, temperature0, ignore_eos. Serial baselines, then mixed-length concurrency4 and8. Explicit cancellation and disconnect occur after streamed text is received; verify request removal, readiness and a subsequent request. Empty prompt must return400. No artificial transfer fence in this HTTP test.

Revisions: Qwen3-0.6B c1899de289a04d12100db370d81485cdf75e47ca; Qwen3-4B1cfa9a7208912126459214e8b04321603b3df60c; KONI8B0172bf7e73977ae213613529f3d2d5400a33f678; Gemma3-1B5b11413a10db4e486ef16a20101fd028f8f2499c. Local model directories are copies of those snapshots; no new download.

## Results

Cache disabled: all four models complete concurrency4/8, cancellation, disconnect, subsequent reuse and invalid-request checks. Each model's12 concurrent outputs exactly match its own serial HTTP baselines (48/48 combined). No remaining request IDs after drain.

Cache enabled: lifecycle/count checks pass for Qwen3 sizes and Gemma; full concurrent output equality is8/12 each, with all discrepancies at2048 input. Gemma first difference24 is after its EOS and must not be treated as a changed completed answer. KONI first cancellation test fails because the subsequent warm-cache output differs from the cold baseline. This is retained as a failed run, not discarded.

Cancellation control corrected: compare warmed state immediately before cancellation with immediately after, while separately recording equality to the original cold baseline. KONI passes both explicit cancellation and disconnect controls with identical before/after outputs; both differ from the cold baseline. Concurrent equality is7/12. Cache-hit counters are positive (34944 in original cases;35072 with the additional warm controls).

## Numerical investigation (#212)

Direct teacher-forced Qwen3-0.6B cold/64-hit/1984-hit and warm concurrent controls show BF16 logit differences up to0.515625, relativeRMS about2.4%; FP32 differences below4.5e-5. However, this direct diagnostic did not reproduce the actual HTTP argmax change and is insufficient alone to explain it. A separate allocation-mode control also did not reproduce that change.

Actual HTTP trace reproduces it: partially cached2K prefill starts64 and uses256-token chunks; fully warmed prefill starts1984. At generated position1, partial-cache top logits for IDs374 and594 are both18.375, so argmax selects374. Warm-cache logits favor594 at18.5 over374 at18.25. Same input hash in both cases. This establishes a numerical tie in the observed HTTP path, not proof of equivalence for all cache histories/models.

Actual HTTP FP32 controls finish on all four models: all lifecycle checks pass and48/48 concurrent outputs match each model's serial baseline. Cold-vs-warm128-token cancellation baselines also match in FP32. Qwen HTTP trace gives the previously tied IDs594/374 scores18.322538/18.220041 (partial) and18.322529/18.220039 (warm), consistently selecting594. The controls support numerical sensitivity as the observed cause; no rounding/tie-breaking change is made to the engine.
