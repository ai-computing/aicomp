# Preserve HTTP connection bursts while accept is delayed (#267)

The common serving listener inherited Python3.10 ThreadingHTTPServer's backlog5. Sixteen clients connecting during a brief accept pause can exhaust it. A real-socket regression holds the accept thread before it starts: the original listener times out; the candidate accepts all16 connections. The candidate sets backlog128 before bind/listen without changing engine admission,request timeouts or request processing.

## Limits

One successful hardware retry supports the backlog hypothesis but does not establish it as the sole reset cause. Counters are host-wide. No before/after throughput gain is claimed because the original did not finish timed measurements. ATOM Qwen4 also reset underc16 on the original listener with no OOM;its native candidate retry passed as detailed below; remaining ATOM and GPU model/routes are pending. Engine concurrency,KV-cache correctness and resource limits are unchanged. Related#267 and#201;not closing either issue.

## ATOM Qwen3-4B cache-on retry

The original native ATOM run reset one SSE connection at input 512, output 128, concurrency 16. The server remained alive and cgroup OOM counters were zero. All 168 token checks completed, but only 11 timed batches completed; the original remains a failed run. Host-wide listen drops increased 82.

With the identical backlog candidate, the retry completed all 24 conditions and 344 responses, matching retained same-route reference outputs. Cache hits were 867456 of 935680 queried tokens; listen drop/overflow increments were both zero. This uses one ATOM execution lane, B1/k3/context9216, prefix caching enabled. At 8192/128/c4, throughput was 23.0725 tok/s and median first SSE 8.43916 s; this is a single warm sample, not a paired cache speedup. Exact raw hashes, package versions and timings are in ../evidence267/qwen4-atom-backlog-controls.json.

The independent retry auditor passed 13 corruption/accounting selfchecks. Combined with the earlier GPU retry, two previously failing configurations now completed, but broader validation remains in progress. No merge or universal reliability claim.

## Qwen3-4B whole-KV paired cache control

Both fresh off/on processes using the same HTTP candidate completed 24 conditions and 344 responses each (48 conditions, 688 responses total), with identical token references and matching streamed text. Host listen drops/overflows increased zero in both runs. All 24 paired timing rows and raw SHA256 fingerprints are retained in ../evidence267/qwen4-whole-cache-pair.json.

At input 8192, output 128, concurrency 4, cache off/on throughput was 31.9662/34.7614 tok/s and median first SSE was 8.49368/7.11375 s. Across all 24 conditions, throughput increased in only 11; changes ranged from -3.72% to +15.26%. These are single ordered off/on samples, not evidence of a universal or repeatable cache speedup, and not a backlog performance comparison.

Both runs queried 935680 prefix tokens. Cache-on hit 850688 tokens, reducing logical transferred tokens from 935680 to 84992. The producer still performs full prefill and copies tensors to CPU before slicing. These counters therefore do not establish reduced producer compute or physical PCIe traffic. Streamed-KV controls remain in progress.
